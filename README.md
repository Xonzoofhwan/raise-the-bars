# raise-the-bars

한국어 UX writing을 다듬는 Claude 스킬. 짧게, 그러나 뜻은 살려서.

`raise the bar`는 기준을 높인다는 뜻이고, 힙합에서 `bars`는 가사의 한 줄을 뜻합니다.
두 뜻이 같은 곳에 착지하도록 지은 이름입니다. UI의 nav bar나 toolbar와는 무관합니다.

## 무엇인가

LLM이 쓴 한국어 UI 문구는 품질이 낮습니다. 이 스킬은 좋은 라이팅을 가르치는
문서가 아니라, **LLM이 반복하는 실패를 교정하는 장치**입니다.

교정 대상 실패 4종:

| id | 실패 | 예 |
|---|---|---|
| **F1** | 문장이 시스템·어시스턴트 시점으로 서술됨 | "요청을 처리했습니다" · "요약을 마쳤어요" · "3명 응답 완료" |
| **F2** | 어색한 경어, 실제로 쓰지 않는 어휘 | "블라인드 처리되었습니다" |
| **F3** | 추상화 수준 오판(양방향) | 에러 코드 노출 ↔ "오류가 발생했습니다"뿐 |
| **F4** | 규칙 환각. 규칙을 일부만 지키거나 없는 규칙을 지어냄 | 존재하지 않는 가이드라인 인용 |

국내 공개 UX 라이팅 가이드 15종과 Material Design에서 **재진술한 근거** 46개
(R-001~R-046)를 추리고, 제품 보이스를 축 5개(종결·경어·용어·공감·밀도)의
프로파일로 받아 규칙을 켜고 끕니다. 문구를 고칠 때는 적용한 규칙 id를 근거로
함께 내놓습니다. 근거를 붙이면 F4(환각)가 줄어든다는 것이 국내 운영 사례에서
확인됐기 때문입니다.

**네 가지 모드로 씁니다.** 문구를 새로 쓰는 **생성**, 초안을 고치는 **검수**,
"이대로 써도 되나요"처럼 고치지 말고 판단만 물을 때의 **확인**, 그리고 기존
문구를 수십 개 이상 받아 **문구들 사이의 어긋남**(어미 혼재, 같은 액션에 다른
어휘, 표기 흔들림)을 찾는 **일괄 진단**입니다.

## 두 가지 원칙

**스킬이 바꿀 수 있는 것은 텍스트뿐입니다.** 컴포넌트 선택, 화면 구성, 기능
유무는 디자이너의 판단입니다. 그 자리에 다 담기지 않는 내용이면 **문구는 내되
무엇이 걸리는지 알려주고, 판단은 사람에게 맡깁니다.** 컴포넌트를 바꾸라고
제안하지는 않습니다. 단, 쓰기 위한 정보(에러의 원인, 사용자가 취할 수 있는
조치)를 되묻는 것은 범위 안입니다. 모르는 채로 "잠시 후 다시 시도해 주세요"를
지어내는 것이 정확히 이 스킬이 막는 실패이기 때문입니다.

**근거 없는 수정은 없습니다.** 모든 수정에 규칙 id가 붙고, 존재하지 않는 id를
지어내는 것은 금지입니다.

## 저장소 구조

```
raise-the-bars/          ← 스킬 본체 (이 폴더가 설치 단위)
├── SKILL.md                  판단 절차
├── references/
│   ├── rules.md              규칙 46개 (R-001~R-046)
│   ├── situations.md         상황·컴포넌트 판정 기준 · 민감 상황 보정
│   ├── profile.md            보이스 축 5개와 규칙 토글
│   └── audit.md              일괄 진단 절차
└── assets/
    └── voice-profile-template.md   제품 프로파일 서식

docs/
└── extracted-rules.md        규칙 46개의 원 레코드(주장·근거·출처)
```

`docs/`는 실행에 쓰이지 않습니다. 스킬을 쓰실 거면 `raise-the-bars/` 폴더만
복사하면 되고, `extracted-rules.md`는 **각 규칙이 어느 자료에서 어떻게
나왔는지** 확인하고 싶을 때 보는 출처 기록입니다.

## 설치

Claude Code 기준, 스킬 폴더를 통째로 복사하면 됩니다.

```bash
# 개인 전역
cp -r raise-the-bars ~/.claude/skills/

# 또는 특정 프로젝트에만
cp -r raise-the-bars <프로젝트>/.claude/skills/
```

이후 "결제 실패 다이얼로그 문구 좀 봐줘" 같은 요청에 스킬이 자동으로 걸립니다.

**프로파일 파일을 만들어 두면 매번 묻지 않습니다.**
`assets/voice-profile-template.md`를 프로젝트 루트나 `docs/`에
`voice-profile.md`로 복사하고, 타깃 사용자와 말투 정도만 채우면 됩니다.
비워 둔 항목은 기본값을 쓰고 무엇을 가정했는지 밝혀줍니다.

## 무엇이 되고 무엇이 안 되는가

스킬을 쓴 쪽과 안 쓴 쪽을 **조건을 가리고** 여러 모델에서 비교했습니다.
아래는 그 결과를 요약한 것입니다. **측정 데이터와 문제지는 공개하지 않았으니,
검증된 사실이 아니라 만든 사람의 보고로 읽어 주세요.**

### 되는 것

**규칙을 지어내지 않습니다.** 이 스킬은 문구를 고칠 때마다 근거 규칙 번호를
함께 내놓는데, **존재하지 않는 번호를 인용한 경우가 여러 모델에 걸쳐 한 건도
없었습니다.** 근거를 밝히게 하면 환각이 억제된다는 가설로 설계했고, 그 부분은
설계대로 작동합니다.

**없는 사실을 덜 지어냅니다.** 스킬 없이 쓰면 입력에 없는 기능·경로·기한을
단정하는 일이 잦은데(예: 원인을 모르면서 "잠시 후 다시 시도해 주세요"),
그것이 크게 줄었습니다.

**선을 넘지 않습니다.** "이 버튼을 없애는 게 낫다" 같은 UI·기능 변경 제안이
거의 나오지 않습니다. 이 스킬이 바꾸는 것은 텍스트뿐이라는 경계가 지켜집니다.

**글이 실제로 나아집니다.** 서로 다른 40개 상황에서, 스킬을 쓴 문구와 안 쓴
문구를 **조건을 가린 채 사람이 각각 채점**했습니다. 스킬을 안 썼을 때 "별로"였던
문구가 **절반 가까이 "좋다"로 바뀌었습니다.** 특히 다이얼로그·빈 화면·에러
안내처럼 **담을 내용이 여러 개인 자리**에서 예외 없이 나아졌습니다.

**이미 괜찮은 문구를 헤집지 않습니다.** 손댈 곳이 거의 없는 문구를 주고 검토를
맡겼을 때, 스킬 없이 쓰면 불필요하게 고쳤지만 스킬을 쓰면 그대로 두거나
꼭 필요한 것만 고쳤습니다.

**담기지 않는 것을 알려줍니다.** 조치가 필요한 에러를 토스트처럼 금방 사라지는
자리에 넣으라고 하면, 사용자가 그 조치를 실행할 시점에 그 문장은 이미 없습니다.
스킬은 **문구를 내면서 그 점을 함께 알립니다.** 그리고 "다이얼로그를 쓰세요"처럼
컴포넌트를 지목하는 대신 **"사용자가 다시 읽을 수 있는 자리가 필요할 수 있습니다"**
처럼 필요한 성질만 말합니다. 무엇으로 만들지는 디자이너의 판단이기 때문입니다.

### 효과가 갈리는 곳

**긴 문구일수록 효과가 큽니다.** 다이얼로그·빈 화면·에러 안내처럼 담을 내용이
여러 개인 자리에서 가장 크게 나아집니다. 반대로 **배지 레이블처럼 10자 안에서
끝나는 자리는 큰 효과가 없을 수 있습니다.** 애초에 고를 여지가 적기 때문입니다.
버튼 레이블은 짧아도 잘 나왔습니다.

한 가지 더 적어 둡니다. **AI에게 채점을 시키면 사람 채점과 결과가 달랐고,
AI는 스킬 쪽에 후했습니다.** 그래서 AI가 매긴 점수는 실제보다 부풀려진 것으로
보아야 합니다. 이 문서에 적은 것은 전부 사람이 직접 채점한 결과입니다.


### 쓰기 전에 알아야 할 것

- **Sonnet 이상에서 쓰세요.** Haiku에서는 스킬이 거의 켜지지 않습니다
- **비쌉니다.** 스킬 없이 쓸 때보다 토큰과 응답 시간이 여러 배입니다.
  문구 하나를 다듬는 값으로는 큰 비용이니, 위에 적은 것을 보고 판단하세요
- **한국어 전용입니다**

### 만들면서 배운 것

검증하면서 규칙을 여러 번 고쳤는데, 대부분 **규칙이 판단을 돕는 대신 막고 있던
지점**이었습니다. 컴포넌트별 글자 수 제한이 더 나은 문구를 막았고, 상황마다
말투를 조금씩 옮기는 12행짜리 표는 실제로 결과를 바꾸지 않았습니다. 둘 다
없앴습니다.

**"~하지 마라"는 지시가 오히려 그 행동을 유발한 경우도 두 번 있었습니다.**
금지어를 적으면 모델이 그 단어에 반응합니다. 그래서 이 스킬의 문안은
가능한 한 "무엇을 한다"로 쓰여 있습니다.

**테스트 문제와 측정 데이터는 공개하지 않았습니다.** 공개하는 순간 정답이
알려진 시험지가 되어, 앞으로 이 스킬이 나아졌는지를 다시 잴 기준을 잃기
때문입니다.
