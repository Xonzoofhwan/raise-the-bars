# 한국어 UX 라이팅 (raise-the-bars)

한국어 UI 문구를 **생성**하거나 **검수**한다.
문구를 만들거나 바꿀 때는 반드시 **어떤 규칙에 근거했는지** 함께 밝힌다.

이 스킬은 좋은 라이팅을 가르치는 문서가 아니라, LLM이 UI 문구를 쓸 때
반복하는 실패를 교정하는 장치다. 교정 대상 실패 4종:

| id | 실패 | 예 |
|---|---|---|
| **F1** | 문장이 시스템·어시스턴트의 세계를 기준으로 서술됨 | "요청을 처리했습니다", "요약을 마쳤어요" |
| **F2** | 어색한 경어, 실제로 쓰지 않는 어휘 | "계셨을", "블라인드 처리되었습니다" |
| **F3** | 추상화 수준 오판 (양방향) | 에러 코드 노출 ↔ "오류가 발생했습니다"뿐 |
| **F4** | 규칙 환각 | 규칙을 일부만 지키거나, 없는 규칙을 지어냄 |

F4 때문에 근거 제시가 강제다. 근거를 밝히게 하면 환각이 억제된다는 것이
실제 운영 사례(라포랩스)에서 확인됐다. 이 스킬의 모든 출력이 그 장치 위에 서 있다.

## 상시 제약 (단계가 아니라 항상 걸린다)

아래 다섯은 절차의 어느 지점에서도 풀리지 않고 **모든 모드에 적용된다.**
절차 안에서 다시 설명하지 않으니, 각 단계를 밟을 때 이 절이 배경에 깔려 있다고
보면 된다.

### 제약 1 · 바꿀 수 있는 것은 텍스트뿐이다

**이 스킬이 바꿀 수 있는 것은 텍스트뿐이다.**
텍스트가 아닌 것을 바꾸라고 제안하는 순간 범위를 넘은 것이다.

하지 않는다:

- 이 메시지가 애초에 필요한지 판단하기
- 컴포넌트 고르기 (토스트냐 다이얼로그냐)
- 버튼이나 UI 요소를 추가하라고 제안하기
- 화면 구성이나 플로우 바꾸기

전부 디자이너의 판단이다. 유용해 보여도 관여하지 않는다.

**단, 쓰기 위한 정보를 되묻는 것은 범위 안이다.** 오히려 라이팅의 전제 조건이다.

- 금지: "이 에러 메시지는 없애는 게 낫습니다" (제품 변경 제안)
- 허용: "이 에러의 원인과 사용자가 취할 수 있는 조치를 알려주세요" (입력 요청)

### 제약 2 · 없는 사실을 만들지 않는다

**입력에 없는 제품 기능·후속 이벤트·경로·수치·기한·도메인을 단정하지 않는다.**
문구에 꼭 필요하면 되묻고, 필수가 아니면 생략한다.
**개별 규칙 적용이 이 조건과 부딪치면 이 조건이 이긴다.**

규칙을 지키려다 사실을 만들어내는 것이 이 스킬의 가장 큰 실패다. 다음 화면을
예고하라고(R-022) 없는 알림 기능을 약속하거나, 조치를 제시하라고(R-026) 확인되지
않은 경로를 지어내는 식이다. 그런 자리에서는 요건을 채우지 말고 무엇을 몰라서
비웠는지 밝힌다.

⚠ 이건 **사실을 모를 때**의 이야기다. 사실은 아는데 **컴포넌트에 담기지
않는** 경우는 4단계에서 따로 다루고, 거기서는 비우거나 멈추는 게 아니라
**문구를 내고 우려를 덧붙인다.**

### 제약 3 · 규칙 id는 R-001~R-046만 실재한다

그 밖의 id가 나오려 하면 그건 환각(F4)이다.
**확신이 없으면 규칙 id 없이 자연어로만 설명한다.**

같은 세션에서 반복 실행할 때는 이미 읽은 내용을 재사용하되, **인용하려는 id의
실재가 확실하지 않으면 `references/rules.md`를 다시 확인한다.**

### 제약 4 · 출력에 넣지 않는 것 셋

- **요청이 지정하지 않은 구성 요소.** 버튼을 달라고 하지 않았으면 버튼 블록을
  만들지 않는다. 요소를 더하는 것은 문구가 아니라 UI 제안이다(제약 1)
- **글자 수·작업 과정 주석.** "(공백 포함 11자)", "후보 셋 중 최종안" 같은
  메모를 문구 옆에 붙이지 않는다. 제약을 지켰는지는 네가 확인할 일이지
  사용자가 읽을 내용이 아니다
- **근거 없는 대안.** 대안은 판단이 실제로 갈리는 지점이 있을 때만 1개다.
  "이렇게도 쓸 수 있어요" 수준이면 넣지 않는다

### 제약 5 · 줄표 자리는 마침표로 끊는다

**줄표(—)를 쓰고 싶은 자리는 아래 셋 중 하나로 간다.** 제안하는 문구에도,
그 문구를 설명하는 문장에도 똑같이 적용된다.

| 줄표를 쓰고 싶은 자리 | 대신 이렇게 |
|---|---|
| 앞말을 풀어 설명할 때 | 문장을 끊고 마침표를 찍는다 |
| 곁들이는 정보일 때 | 괄호에 넣는다 |
| 앞뒤를 대비할 때 | 쉼표로 잇거나 "반대로"를 쓴다 |

⚠ **이 문서 자체는 줄표를 쓰고 있다.** 문서의 문체를 따라 쓰지 말고 이 제약을
따른다. 줄표는 한국어 UI에서 쓰지 않는 부호이고, 쓰면 기계가 쓴 티가 난다.

## 0단계 · 모드 판정 (여기서 한 번만 가른다)

요청을 받으면 먼저 어느 모드인지 정하고, **그 모드가 통과할 단계만 밟는다.**
뒤에서 모드를 다시 가르지 않는다.

**프로파일은 모드와 무관하게 쓴다.** 프로파일 확보는 절차가 아니라 **입력
확보**라, 아래 표에서 어느 칸에 해당하든 이 값이 걸린다. 일괄 진단도 마찬가지다.

**기본값은 "없음"이다.** 프로파일이 이미 주어졌거나 이 세션에서 읽은 적이
있으면 그 값을 쓰고, 아니면 기본 프로파일로 진행한다. 파일을 찾아볼 수 있는
환경이면 프로젝트 루트와 `docs/`의 `voice-profile.md`가 그 자리다.
→ `references/profile.md`

| 모드 | 언제 | 통과하는 것 |
|---|---|---|
| **생성** | 새 문구를 써 달라 | 판정 전부(1~5단계) · 산출 전부(6~8단계) |
| **검수** | 초안을 고쳐 달라 | 판정에서 **4단계 제외** · 산출 전부 · **보존 지시 우선** |
| **확인** | 고쳐 달라는 게 아니라 **판단**을 물음 | 판정 없음 · 판단만 답함 · **규칙 id 미노출** |
| **일괄 진단** | 기존 문구를 **수십 개 이상** 한꺼번에 | 절차는 `references/audit.md` · **프로파일과 상시 제약은 그대로 걸린다** |

**파일이 없을 때의 처리만 모드마다 다르다.**

| 모드 | 파일이 없으면 |
|---|---|
| 생성 · 검수 | 2단계의 세 질문을 **한 번만** 묻고, 답으로 파일을 만들자고 제안 |
| 확인 | 묻지 않는다. 기본 프로파일로 판단하고 그렇게 했다고 밝힌다 |
| 일괄 진단 | 묻지 않는다. 받은 문구에서 **역추정**하고 파일을 만들자고 제안 (`audit.md` 5단계) |

### 확인 모드

**"이대로 써도 되나요", "오탈자만 봐 주세요"처럼 고쳐 달라는 것이 아니라
판단을 물은 경우.** 법무·규격이 확정한 문구, 시스템이 주는 데이터 표기가
여기 해당한다.

- **규칙 id·내부 분류 이름·"이 스킬"을 답에 쓰지 않는다.** 사용자는 이 체계를
  모르고, 물어본 것은 판단이지 이 도구의 작동 방식이 아니다
- 요청받은 판단을 **분명히 답한다.** 판단을 피하고 다른 이야기를 하지 않는다
- **고치라고 하지 않았으면 고친 문구를 내밀지 않는다.** 문제를 발견하면
  무엇이 문제인지만 말하고, 수정은 요청받은 뒤에 한다
- 사용자가 그다음에 "그럼 고쳐 줘"라고 하면 그때부터 검수 모드다.
  거기서는 규칙 id와 함께 근거를 밝힌다(R-043)

### 검수 모드

⚠ **사용자가 보존을 지시한 표현은 하우스 스타일보다 우선한다.** 버튼 레이블·
고유 표기·수치를 "바꾸지 말라"고 했으면, 규칙(R-023·R-024 등) 위반 소지가
있어도 **바꾸지 않고 지적만 한다.** 보존 지시를 규칙으로 덮어쓰는 순간
사용자가 지키려던 것이 사라진다.

고칠 것이 없으면 없다고 말한다. 규칙 위반이 없는데 취향으로 고치지 않는다.

### 일괄 진단 모드

개별 규칙 위반보다 **문구들 사이의 어긋남**(어미 혼재, 같은 액션에 다른 어휘,
표기 흔들림)이 관심사이고, 절차가 다르다.
"이 문구들 좀 봐줘", "전체적으로 통일해줘" 같은 요청이 여기 해당한다.

## 판정 (1~5단계). 무엇을 담을지 정한다

### 1단계 · 입력 확인

여섯 가지가 필요하다. 각각 없으면 판정할 수 없는 것이 다르고,
**어디서 오는지가 다르다.**

| 항목 | 어디서 오는가 | 없으면 판정 불가능한 것 |
|---|---|---|
| **컴포넌트** | 요청에서 받는다 | 분량·형식 제약 |
| **상황** | **맥락에서 네가 판정한다** | 무엇을 담아야 하는지 |
| **타깃 사용자** | 프로파일 파일 | 전문 용어를 써도 되는지 |
| **사용자 목표** | 프로파일 파일 | 추상화 수준 (F3) |
| **서비스 목표** | 프로파일 파일 | 사용자 편의와의 균형 |
| **보이스 축** | 프로파일 파일 | 규칙 토글 |

셋의 성격이 다르다.

- **컴포넌트**는 디자이너가 정한 것이라 받는다. 없으면 묻는다. 다만 사용자는
  "토스트", "확인 다이얼로그"처럼 자연어로 말하지 C-03이라고 하지 않는다
- **상황은 묻지 않는다.** 사용자의 말과 맥락에서 어느 상황에 가까운지 판정하는
  것은 네 일이다. 분류 이름(P-07a 같은)을 사용자에게 노출하지 않는다
- **나머지 넷은 제품 단위로 고정**이라 파일로 한 번 받는다. 매 요청마다 물으면
  스킬을 쓰는 비용이 얻는 것보다 커진다

### 2단계 · 프로파일 확보

**파일이 있는지는 0단계에서 이미 봤다.** 여기서는 없을 때 무엇을 할지 정한다.

**기본값은 "없음"이다.** 프로파일 파일이 눈앞에 주어졌거나 이미 읽은 적이
있으면 쓰고, 아니면 기본 프로파일로 바로 진행한다.
**프로파일을 모른다는 이유로 작업을 멈추지 않는다. 대신 무엇을 가정했는지
반드시 출력에 밝힌다.**

파일을 어디서 찾는지, 서식이 무엇인지, 빈칸과 제품 불일치를 어떻게 처리하는지,
기본 프로파일 값이 무엇인지는 전부 → `references/profile.md`

#### 파일이 없으면 한 번만, 이 형식으로 묻는다

세션에서 처음 문구를 요청받았고 파일도 없을 때만 묻는다. **답을 받으면 그
세션 내내 재사용하고 다시 묻지 않는다.** 예시를 함께 주지 않으면 답이
제각각이 되고, 그러면 판정도 흔들린다.

> 문구를 쓰기 전에 세 가지만 확인할게요. 한 번만 여쭤보고 계속 씁니다.
>
> **1. 어떤 분들이 쓰나요?** 이분들이 평소 쓰는 말로 써야 해서요
> 직업·역할·연령대처럼 구체적으로 알려주세요.
> 예: 20~30대 일반 소비자 / 사내 개발자 / 병원 원무과 직원
> 이분들이 일상적으로 쓰는 용어가 있으면 함께요 (예: API 키, 처방전, 정산)
>
> **2. 이 제품은 사용자에게 무엇을 해주나요?** 어디까지 설명해야 할지 정해서요
> 예: 주문한 상품이 어디쯤 왔는지 알려준다 / 팀원과 문서를 같이 고친다
>
> **3. 사용자가 꼭 거쳐야 하는 절차가 있나요?** 없으면 '없음'
> 예: 본인 확인 / 첫 프로젝트 만들기 / 마케팅 수신 동의
>
> 말투가 정해져 있으면 함께 알려주세요 (해요체·합니다체·명사형 중 하나).
> 없으면 기본값으로 쓰고 무엇을 가정했는지 밝히겠습니다.

질문 옆의 설명은 **왜 묻는지**를 밝히는 것이다. "무엇을 정한다"는 스킬 쪽
사정이라 사용자에게는 답할 이유가 되지 않는다. 사용자가 왜 답해야 하는지
보여야 답이 정확해진다.

**답을 받으면 그 요청의 문구를 먼저 내놓고, 출력 끝에 파일 제안을 붙인다.**
빠뜨리면 다음 세션에서 같은 질문을 또 하게 된다. 사용자가 이 스킬을 두 번째로
쓸 때 겪는 첫인상이 여기서 갈린다.

> 이 답변들을 `voice-profile.md`로 저장해 두면 다음부터는 묻지 않아요.
> 서식은 `assets/voice-profile-template.md`에 있고, 프로젝트 루트나 `docs/`에
> 두면 됩니다. 만들어 드릴까요?

사용자가 답하지 않고 그냥 써 달라고 하면 기본 프로파일로 쓴다.

#### 예외. 에러 문구는 매번 묻는다

**에러 문구인데 원인과 조치를 모르면 반드시 묻는다. 예외 없음.** (R-031)
이건 프로파일 파일로 해결되지 않는다. 에러마다 원인과 조치가 다르기 때문이다.

모르는 채로 "잠시 후 다시 시도해 주세요"를 쓰는 것이 LLM의 대표 실패다.
원인을 모르면 그 재시도가 통할지도 모르는 것이고, 통하지 않을 조치를
제시하는 것은 R-029 위반이다.

### 3단계 · 상황 판정과 컴포넌트 확인

`references/situations.md`를 좌표 삼아 **상황을 판정하고**, 컴포넌트를 확인한다.

**상황이 '무엇을 말할지'를, 컴포넌트가 '얼마나 길게, 어떤 형식으로'를 정한다.**
둘은 포함 관계가 아니라 교차 관계다. 하나의 상황이 여러 컴포넌트로 표현되고,
하나의 컴포넌트가 여러 상황을 담는다.

**상황 목록은 사용자에게 고르라고 내미는 메뉴가 아니다.** 판정은 네가 한다.
딱 맞는 항목이 없으면 가장 가까운 것으로 판정하고 그렇게 판정했다고 밝힌다.
완결된 분류가 아니라 규칙을 고르기 위한 좌표다.

에러는 반드시 귀책으로 나눈다:

- **P-07a** 사용자 입력 원인. 무엇이 잘못됐고 어떻게 고치는지
- **P-07b** 시스템·연결 원인. **여기서 F1 규칙이 뒤집힌다** (아래 「자주 틀리는 지점」)

이 갈림을 맥락으로 판정할 수 없으면 그때만 확인한다. 분류 이름으로 묻지 말고
**"이 실패가 사용자 입력 때문인가요, 시스템 장애인가요"**처럼 판정에 필요한
사실만 묻는다.

**컴포넌트 이름이 목록에 없어도 멈추지 않는다.** 네 가지 축(분량·지속·맥락·형식)만
판정하면 된다. 특히 **자동으로 사라지는가**(조치를 담을 수 있나)와
**화면 밖에서 읽히는가**(혼자 서야 하나)가 규칙을 발동시킨다.
값이 애매하면 그 값만 묻는다: "이 배너는 자동으로 사라지나요?"

### 4단계 · 담기지 않는 것이 있으면 알린다 (생성 모드만)

상황이 요구하는 내용이 그 자리에 다 담기지 않을 때가 있다.
대표 사례가 **조치가 필요한 에러 × 토스트**다. 토스트는 자동으로 사라져서
사용자가 조치를 실행할 때 그 문장이 이미 없다.

**그래도 문구는 낸다.** 요청받은 자리에 맞춰 쓸 수 있는 만큼 쓰고,
**우려되는 지점을 뒤에 덧붙인다. 판단은 사람이 한다.**

```
[문구]

적용한 규칙
- …

우려되는 점
- 조치("다른 카드로 다시 시도")는 토스트가 사라진 뒤에 하는 일이라
  사용자가 다시 읽을 수 없습니다. 이대로 둘지는 확인이 필요합니다.
```

⚠ **컴포넌트 이름을 대지 말고 필요한 성질을 말한다.**
어느 컴포넌트가 그 성질을 갖는지는 디자이너가 안다. 이름을 대는 순간
그 판단을 대신하는 것이 되어 범위를 넘는다(상시 제약 1).

| 이름을 댄 것 (범위 밖) | 성질을 말한 것 (범위 안) |
|---|---|
| 다이얼로그가 더 적합할 수 있어요 | 이 조치는 사용자가 실행할 때까지 **화면에 남아 있어야** 합니다 |
| 배너로 바꾸는 게 낫습니다 | 사용자가 **다시 읽을 수 있는 자리**가 필요할 수 있습니다 |
| 인라인 메시지를 쓰세요 | **입력한 자리에서 바로 보이는** 편이 나을 수 있습니다 |
| 토스트로는 안 됩니다 | **잠깐 스쳐가는 자리**로 두어도 되는 내용인지 확인이 필요합니다 |

**"~가 더 적합하다·낫다"는 평가도 이름과 함께 오면 범위 밖이다.**
성질만 말하고 그 성질을 어디에 담을지는 넘긴다.

⚠ **우려가 없으면 이 절은 출력하지 않는다.** 담기는 자리에까지 붙이면
매번 나오는 군더더기가 된다.

### 5단계 · 민감 상황과 극소 자리 판정

둘 다 **네가 판정한다.** 사용자가 알려주는 것이 아니다.

**민감 상황**은 셋 중 하나면 해당한다: **되돌릴 수 없다 / 손해가 걸렸다 /
문제를 안고 들어왔다**(에러·장애, CS·문의). 결제 완료처럼 "잘 됐나" 싶은
자리는 해당하지 않는다. 넓게 잡으면 보정이 기본값이 되어 의미가 없어진다.

해당하면 **밀도와 공감을 한 단계씩 올리고** 단정적 표현을 피한다.
경어는 **프로파일에서 켠 제품만** 올린다(기본은 끔).
그 밖의 상황에서는 프로파일 기본값을 그대로 쓴다. → `references/situations.md`

⚠ **극소 자리. 버튼 레이블·배지·짧은 토스트처럼 몇 글자로 끝나는 자리는
우선순위가 뒤집힌다.** 간결·동사형·용어 최소가 거기서는 정보를 깎는다.
행동의 대상, 무엇에 일어났는지, 형식 예시, 등급 서열이 규칙보다 먼저다.
→ `references/situations.md`의 「극소 자리」 절

## 산출 (6~8단계). 어떻게 내놓을지 정한다

### 6단계 · 규칙 적용

세 겹으로 적용한다.

1. **항상 적용 규칙**. 프로파일과 무관하게 적용. → `references/rules.md`
2. **프로파일 의존 규칙**. 프로파일 값이 켜고 끈다. → `references/profile.md`
3. **상황별 처리**. 상황마다 강제로 걸리는 규칙이 있고, 5단계에서 민감 상황으로
   판정했으면 톤을 통째로 보정한다. → `references/situations.md`

처음 실행할 때는 세 파일을 모두 읽는다.

### 7단계 · 자기 점검

출력 전에 확인한다. 앞의 세 항목이 이 스킬이 존재하는 이유다.
각 항의 설명은 근거로 단 문서에 있다.

- [ ] 시스템이나 AI가 화자·행위자로 등장하지 않는가 (F1)
- [ ] 1인칭이 없어도 화자가 AI인 문장이 남아 있지 않은가 (R-033 · 아래 절)
- [ ] '당신', '사용자', '회원님'을 주어로 넣지 않았는가 (R-035)
- [ ] 입력에 없는 기능·경로·수치·기한을 단정하지 않았는가 (제약 2)
- [ ] 요청에 없는 버튼·화면 요소를 출력에 넣지 않았는가 (제약 1·4)
- [ ] 인용한 규칙 id가 전부 실재하는가 (제약 3)
- [ ] 내부 용어·에러 코드가 남아 있지 않은가 (R-027)
- [ ] 제시한 조치가 실제로 통하는가 (R-029)
- [ ] 간결하게 만든다고 필수 정보를 버리지 않았는가 (R-019)
- [ ] 종결 체계가 프로파일과 일치하는가 (R-001)
- [ ] 소리 내어 읽었을 때 어색하지 않은가 (R-015)

### 8단계 · 근거와 함께 출력

모드는 0단계에서 이미 갈렸다. 여기서는 형식만 고른다.

**생성**은 기본이 1안이다. 프로파일이 미확정이거나 판단이 갈리는 지점이 있으면
갈림을 보여주는 대안을 1개까지 추가한다.

```
[문구]

적용한 규칙
- R-023 (CTA는 결과를 예고하는 동사로): '확인' 대신 '삭제하기'
- R-026 (에러 3요소): 원인과 해결 방법 포함

가정한 입력 (맥락에서 추론한 경우만)
- 타깃: 일반 사용자 / 프로파일: 기본값
- 이유를 덧붙일 때는 문장을 끊는다. `voice-profile.md`가 없어 기본값으로 판정했다
```

⚠ **근거 줄과 가정 줄에서 줄표가 새기 쉽다.** `프로파일: 기본값 — 파일이 없어서`
처럼 쓰지 말고 위 예시처럼 마침표로 끊는다(제약 5).

**검수**는 수정 전후를 나란히 보여준다.

```
수정 전: [원문]
수정 후: [수정문]

- R-032 (시스템 행위를 결과로): "업로드를 완료했습니다"·"업로드가 완료되었습니다"
  → "업로드가 끝났어요"
```

**확인**은 판단과 이유만 낸다.

```
[요청받은 판단: 이대로 가능 / 불가 · 오탈자 있음 / 없음]
[그렇게 본 이유 한두 줄. 문구 자체의 근거로]
```

## 자주 틀리는 지점: 시점 · 좌표계 (F1)

전체 규칙은 `references/rules.md`에 있다. 아래 한 가지만 여기 두는 이유는
**문구를 판정하는 규칙이 아니라 이 스킬을 실행하는 너의 습관을 교정하는
규칙**이기 때문이다.

문장이 **시스템의 세계**를 기준으로 서술되면 안 된다.
고칠 대상은 주어가 아니라 **좌표계**다.

| 유형 | 나쁜 예 | 수정 방향 |
|---|---|---|
| F1-a 시스템이 행위자 | 요청을 처리했습니다 · 동기화가 완료되었습니다 | 사용자에게 생긴 결과로 |
| F1-b 어시스턴트 레지스터 누출 | 제가 분석해 드렸어요 · 요약을 마쳤어요 | 화자를 브랜드로 되돌린다 |
| F1-c 기준점이 시스템 데이터 | 3명 응답 완료 | 2명 남았어요 |

**수정은 삭제와 재구성이지 삽입이 아니다.** 한국어는 주어 생략이 자연스러워
대부분 삭제만으로 해결된다. '당신'이나 '회원님'을 넣으면 더 나빠진다 (R-035).

### F1-b는 너 자신에게 적용되는 규칙이다 (R-033)

나머지 45개가 문구를 판정하는 규칙이라면, 이것은 **이 스킬을 실행하는 모델의
습관을 교정하는 규칙**이다. 너는 방금 한 일을 보고하는 대화 습관이 있고,
UI 문구를 쓸 때 그 시점이 남는다. 사람은 이 실수를 하지 않아서 국내 가이드
어디에도 이 항목이 없다.

**표면에 1인칭이 없어도 누출이다.** 한국어는 주어를 생략하므로 '제가'를 찾는
것으로는 잡히지 않는다. 판정 질문은 이것이다.
**이 문장을 말하는 주체가 브랜드인가, 방금 작업을 수행한 AI인가?**

| 겉보기 | 실제 화자 | 고친 문구 |
|---|---|---|
| 요약을 마쳤어요 | AI | 회의록이 3줄로 정리됐어요 |
| 무엇을 도와드릴까요? | AI | 무엇을 찾고 있나요? |
| 답변을 다시 생성할게요 | AI | 다시 만들기 |

**AI 기능을 다루는 제품에서 가장 놓치기 쉽다.** 실제로 AI가 수행한 작업이니
AI를 화자로 두는 게 자연스러워 보이지만, 화면의 화자는 여전히 브랜드다.
그리고 **컴포넌트가 명시되지 않은 요청**("이 기능 끝나면 뭐라고 표시하지?")일수록
레지스터가 대화 쪽에 머물러 누출이 잘 난다.

**예외.** 귀책이 시스템에 있으면 반대로 시스템을 주체로 명시한다 (R-036).
"서버 점검 중이에요"를 사용자 기준으로 바꾸면 사용자 잘못처럼 읽힌다.
P-07b(시스템 에러)와 P-09(제한·불가)가 이 예외에 해당한다.
**규칙이 상황에 따라 뒤집히는 유일한 지점**이므로 분기를 놓치지 않는다.
