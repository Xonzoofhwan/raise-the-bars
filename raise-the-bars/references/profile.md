# 프로파일 — 축 5개와 규칙 토글

프로파일은 제품의 보이스를 규칙 토글로 번역하는 층이다.

```
프로파일 = 기본값(제품 단위) + 상황별 이동값(민감도 높은 축만 → situations.md)
```

**전역 설정 하나가 아니다.** 같은 제품 안에서도 상황에 따라 톤이 움직인다 —
Material은 에러 상황에서 톤이 지지적·상세한 쪽으로 이동해야 한다고 명시하고,
오늘의집은 하나의 봇으로 모든 문구를 소화하지 못해 도메인별로 나눴다.
그래서 기본값과 이동값을 분리한다.

## 축 요약

| 축 | 성격 | 값 | 민감 상황에서 |
|---|---|---|---|
| **종결** | 택1 (중간 없음) | 해요체 / 합니다체 / 명사형 | **고정 — 절대 안 움직임** |
| **경어** | 정도 | 낮음 / 중간 / 높음 | **+1** |
| **용어** | 정도 | 최소 / 중간 / 적극 | 고정 |
| **공감** | 정도 | 낮음 / 중간 / 높음 | **+1** |
| **밀도** | 정도 | 간결 / 중간 / 상세 | **+1** |

종결만 성격이 다르다 — 정도 문제가 아니라 택1이고, 섞이는 것 자체가 결함이다.
나머지 넷은 정도를 조절한다.

**축 값은 대부분의 상황에서 그대로 쓴다.** 상황마다 조금씩 흔드는 것은 실익이
없었다 — 문구를 가르는 것은 상황별 강제 발동 규칙이지 ±1이 아니다.
**민감 상황**(사용자가 불안하거나, 되돌릴 수 없거나, 손해가 걸린 자리)에서만
경어·공감·밀도를 한 단계씩 올린다. 판정과 보정값은 `situations.md`.

종결과 용어는 민감 상황에서도 움직이지 않는다. 종결이 흔들리면 그 자체가
R-001 위반이고, 사용자가 아는 용어의 범위는 상황에 따라 바뀌지 않는다.

## 축별 토글 매핑

### 종결 — 민감도 0

| 값 | 발동 |
|---|---|
| 해요체 | R-001 = 해요체. 이후 모든 출력의 종결 고정 |
| 합니다체 | R-001 = 합니다체 |
| 명사형 | R-001 = 명사형. 단 **다이얼로그·바텀시트·빈 화면에서는 문장형 허용** — 명사형만으로는 이유를 서술할 수 없다 |

"상황·맥락 불문 통일"이 이 축의 핵심이다. 에러에서 갑자기 격식체로,
완료에서 갑자기 해요체로 흔들리면 그 자체가 R-001 위반이다.

### 경어 — 민감도 낮음

**어느 값이든 존댓말이다.** 이 축이 조절하는 것은 존댓말이냐 반말이냐가 아니라
**높임의 강도**다. 하한은 반말이 아니라 '경박하지 않은 기본 존댓말'이고,
상한이 극존칭이다.

| 값 | 어떤 말투인가 | 발동 |
|---|---|---|
| 낮음 | 기본 존댓말. '~시', '계시다', '께'를 쓰지 않는다. "생년월일을 입력해 주세요" | R-002 ON, R-003 ON |
| 중간 | 호칭과 의문형에서만 높임을 유지. "삭제하시겠습니까?" | R-002 부분 적용 |
| 높음 | 극존칭. '~시', 계시다, 께를 적극 사용 | R-002 OFF, R-004 확대 적용 |

낮음이어도 R-004(질문형 경어 허용)는 살아 있다. 사용자에게 무언가를 묻는
자리에서 높임을 다 빼면 단정처럼 읽히기 때문이다. 기계적으로 '~시'만 빼서
비문이 나오면 R-003으로 문장을 재구성한다.

**민감 상황에서 한 단계 올릴지는 별도 선택이다.** 프로파일 파일의
"민감 상황에서 높임을 올릴까요?" 항목에서 받고, **기본은 끔**이다.
탈퇴·에러 같은 자리에서 정중함을 높임 어미로 표현하는 제품이 있고
아닌 제품이 있어서 갈린다 — 병원 앱의 "탈퇴하시기 전에"는 자연스럽지만
개발자 도구에서는 과하다. 꺼져 있으면 정중함은 어미가 아니라 밀도 보정
(무엇을 얼마나 말해주느냐)이 담당한다.

### 용어 — 민감도 낮음

| 값 | 발동 |
|---|---|
| 최소 | R-012 = 최소 분기 (풀어쓰기), R-014 ON (한자어 풀기) |
| 중간 | R-012 = 최소 분기, R-014 완화 |
| 적극 | R-012 = 적극 분기, R-014 OFF |

**적극이어도 초출 설명은 제품 고유 개념에만 붙인다.** 타깃이 이미 쓰는 용어를
설명하는 것은 R-018(아는 정보 생략)과 충돌한다 — 개발자에게 '엔드포인트'를
설명할 필요는 없다. 설명 대상은 그 제품이 만든 이름('스마트 태그' 같은)이다.

⚠ **R-010(공급자 언어 금지)은 이 축과 무관하게 항상 ON이다.**
용어 허용은 사용자가 이미 쓰는 도메인 용어(예: 개발자에게 'API 키')를
쓴다는 뜻이지, 내부 시스템 용어·예외 상태·에러 코드를 노출해도 된다는 뜻이 아니다.

### 공감 — 민감도 중간

정보를 전달하는 순간 사용자가 어떤 감정일지 고려하고 반응하는 정도다.

| 값 | 발동 |
|---|---|
| 낮음 | R-037 OFF (사실 전달만) |
| 중간 | R-037 조건부 — 완료(P-06)와 시스템 에러(P-07b)에서만 |
| 높음 | R-037 ON |

### 밀도 — 민감도 높음

| 값 | 발동 |
|---|---|
| 간결 | R-016·R-017·R-018 강하게 |
| 중간 | R-016 ON, R-018 완화 |
| 상세 | R-016 완화, R-017만 유지 |

⚠ **R-019(필요한 내용은 쪼개서 유지)는 이 축과 무관하게 항상 ON이다.**
'간결'이 정보를 버려도 된다는 뜻이 되는 순간 F3(추상화 오판)으로 넘어간다.
줄이는 게 아니라 쪼갠다.

## 축에서 뺀 것 — 브랜드 특성으로 받는다

아래 둘은 이전에 축이었으나 뺐다. **모든 제품이 정해야 하는 값이 아니라
특수한 브랜드에만 해당하는 성격**이기 때문이다. 축으로 두면 대부분의 제품이
"기본값"만 고르고 지나가는 빈 설정이 된다.

둘 다 프로파일 파일의 **브랜드 특성** 항목에 자유 서술로 적고, 적혀 있을 때만
해당 규칙이 켜진다.

### 위트

> 예: "기능 소개에서는 가벼운 위트를 쓴다"

적혀 있지 않으면 R-041의 기본값이 적용된다 — **과업 수행 지점(에러·확인·입력·
진행·제한·푸시)에는 쓰지 않는다.** 배민조차 기능 소개에만 위트를 쓰고 과업
수행에는 전혀 쓰지 않는다. 위트를 쓰는 브랜드도 그 범위는 좁다.

R-040(보편 어휘)은 위트를 허용해도 계속 적용된다 — 유행어·은어·밈은 별개 문제다.

### 확신 톤

> 예: "확신을 주는 톤. '바로', '가장' 같은 수식어와 느낌표를 쓴다"

적혀 있으면 R-020(확신 수식어 허용)이 켜지고 R-016(잡초 제거)이 완화된다.
강남언니가 이 경우다 — 의료 정보라는 도메인 특성상 불안한 사용자에게 확신을
주는 것이 브랜드 전략이다.

**공감 정도를 높이는 것으로는 대체되지 않는다.** "고생 많으셨어요"(공감)와
"가장 빠른 방법이에요!"(확신)는 다른 문장이다. 다만 확신 톤이 필요한 제품이
드물어서 축이 아니라 브랜드 특성으로 옮겼다.

## 축 매핑 밖의 프로파일 의존 규칙

규칙 레코드에서 `프로파일: yes`인데 위 축 매핑 표에 없는 규칙이 셋 있다.
어디에 매여 있는지를 여기서 명시한다 — 표에 없다고 프로파일과 무관한 것이
아니다.

| 규칙 | 무엇에 매여 있는가 | 처리 |
|---|---|---|
| **R-007** 긍정형 전환 | **공감 축** — 공감이 높을수록 강해진다 | 축과 함께 켜지되, P-09에서는 R-008이 덮어쓰고 P-07(에러)에서는 사실 보존(R-026·R-028)이 우선한다 |
| **R-038** 감정의 두 방향 | **브랜드 특성 '확신 톤'** | 아래 "축에서 뺀 것" 절의 확신 톤 서술이 이 규칙의 내용이다. 특성이 적혀 있을 때만 확신 방향이 켜진다 |
| **R-042** 표기 규칙 사전 확정 | **제품이 정한 표기표** | 프로파일 파일의 표기 규칙 항목에서 받는다. 표기표가 없으면 가장 흔한 표기를 쓰고 무엇을 가정했는지 밝힌다 |

## 기본 프로파일

프로파일이 주어지지 않으면 이 값을 쓰고, 가정했다고 명시한다.

```
종결 해요체 / 경어 낮음 / 용어 최소 / 공감 중간 / 밀도 간결
브랜드 특성: 없음 (위트·확신 톤 모두 꺼짐)
```

## 값은 파일로 받는다

제품 단위로 고정되는 값(축 5개 + 브랜드 특성 + 필수 입력 3종 + 표기 규칙)은
**`voice-profile.md` 파일 하나로 받는다.** 매 요청마다 묻지 않기 위해서다.
파일 처리 규칙의 본문은 여기다 — SKILL.md는 이 절을 가리키기만 한다.

- 찾는 위치: 프로젝트 루트, `docs/` — **두 곳만**
- 서식: `assets/voice-profile-template.md`
- 파일이 없으면 SKILL.md 「프로파일 확보」 단계의 고정 질문 형식으로
  **한 번만** 묻고, 답을 받으면 파일을 만들어 두자고 제안한다
- 빈칸은 그 항목만 기본값을 쓰되 무엇을 가정했는지 출력에 밝힌다

**파일을 열어볼 수 있는 환경이라면** 위 두 곳을 확인한다. 있으면 타깃 사용자·
사용자 목표·서비스 목표·보이스 축 네 항목이 해결되므로 **묻지 않는다.**
파일을 열 수 없는 환경이면 기본 프로파일로 진행하고 그렇게 했다고 밝힌다.

**하위 디렉터리를 뒤지지 않는다.** 한 저장소에 여러 제품이 있을 수 있고,
엉뚱한 제품의 프로파일을 집으면 타깃도 말투도 어긋난 문구가 나온다.
두 곳에 없으면 없는 것으로 본다.

**같은 두 곳에 이름이 다른 보이스 문서가 있으면 써도 된다** —
`brand-voice.md`, `tone-of-voice.md`, 디자인 시스템의 보이스 절 같은 것들이다.
서식이 달라 축 값이 그대로 들어 있지 않을 뿐, 판정에 필요한 정보는 거기 있다.

⚠ **단, 무엇을 프로파일 대신 썼는지 반드시 밝힌다.** 밝히지 않으면 사용자는
자기가 만든 프로파일이 반영된 줄 안다. 축으로 옮기면서 추론한 값이 있으면
그것도 함께 적는다 — "브랜드 문서에 '전문가에게 말하듯'이라 적혀 있어
용어를 '적극'으로 봤습니다"처럼.

**파일을 찾았으면 지금 요청과 같은 제품인지 확인한다.** 프로파일 첫 줄의
제품 이름과 요청 내용이 어긋나면(예: 파일은 병원 예약 앱인데 요청은
장바구니 문구) 값을 가져다 쓰지 말고 사용자에게 확인한다 —
축 값만 빌려 쓰는 것도 안 된다. 타깃이 다르면 용어 판정이 통째로 틀린다.

**사용자가 값을 바꾸면** 그 요청에만 적용한다. "이번엔 타깃이 달라"처럼
한 번 바꾼 값을 계속 쓸 것 같으면 파일을 고치자고 제안한다.

## 프로파일을 처음 정하는 제품이라면

다섯 값을 한 번에 다 묻지 말고, 갈림이 큰 것부터 확인한다.

1. **종결** — 해요체 / 합니다체 / 명사형 중 무엇인가 (가장 눈에 띄는 갈림)
2. **용어** — 타깃 사용자가 도메인 용어를 이미 쓰는가
3. **경어** — 기본 존댓말인가, 호칭에 높임을 유지하는가, 극존칭인가

나머지(공감·밀도)는 기본값에서 시작해 결과물을 보며 조정하는 편이 빠르다.
기존 제품이면 실제 화면 문구 3~5개를 받아 값을 역추정할 수 있다 —
추정한 값은 반드시 명시하고 확인받는다.

## 축이 아닌 것 — 파생값 주의

**친근함, 신뢰감, 전문성은 축이 아니라 결과다.**
친근함 ≈ 종결 + 경어 + 공감의 조합이고, 전문성 ≈ 용어 + 공감의 조합이다.
축으로 두면 "친근함 높음 + 경어 높음" 같은 모순 설정이 가능해진다.
사용자가 "친근하게 해주세요"라고 하면 축 값으로 번역해 받고
(예: 해요체 + 경어 낮음 + 공감 중간), 번역 결과를 명시하고 확인받는다.

## 축 독립성 근거 (관측)

| | 종결 | 경어 | 용어 | 공감 |
|---|---|---|---|---|
| 토스 | 해요체 | 낮음 | **최소** | **높음** |
| 스켈터랩스 (B2B) | 해요체 계열 | 낮음 | **적극** | **낮음** |
| 강남언니 | 존댓말 | 중간 | 최소 | 중간 + **확신 톤** |
| 구름 | — | — | 적극 | 중간 |

토스와 스켈터랩스는 경어가 같은데 용어·공감이 반대다 (경어 ⊥ 용어, 용어 ⊥ 공감).
"B2B = 격식체"는 틀린 가정이다 — 스켈터랩스는 B2B인데 극존칭을 쓰지 않는다.
강남언니는 공감이 특별히 높지 않은데도 톤이 강한데, 그것이 확신 톤을
축이 아니라 브랜드 특성으로 뺀 이유다.
