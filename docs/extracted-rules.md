## 읽는 법

레코드 단위는 **재료가 아니라 근거**다. 하나의 재료에서 여러 레코드가 나오고,
하나의 레코드에 여러 출처가 붙는다. 원문은 옮기지 않았고 전부 재진술이다.

각 레코드 필드:
- **주장** — 규칙 한 줄
- **근거** — 왜 그런가. 목록에 없는 케이스를 처리하게 해주는 부분
- **적용** — 어떤 문구 유형에서
- **프로파일** — `yes`면 제품 보이스에 따라 갈림(옵션), `no`면 항상 적용
- **민감도** — 상황에 따라 값이 흔들리는 정도 (0 / 낮음 / 중간 / 높음)
- **충돌** — 상충하는 레코드 id
- **출처** — 아래 S-id

# A. 문체 · 종결

### R-001 · 종결 체계 통일
- **주장** 제품 안 모든 문구의 문장 종결 체계를 하나로 통일한다
- **근거** 어미가 섞이면 같은 기능에 다른 어감이 붙어 한 제품이 여러 사람처럼 말하게 된다.
  네 팀이 독립적으로 같은 증상을 진단했다는 점에서 이 규칙의 강도가 높다
- **적용** 전체 / **프로파일** yes(어느 체계인지) / **민감도** 0
- **출처** S-01(상황·맥락 불문 통일), S-09(같은 액션에 다른 어휘), S-04(같은 기능에 다른 어미 혼재), S-06(한 화면 안 온도 차)

### R-002 · 과도한 경어 제거
- **주장** '~시', '계시다', '여쭈다', '께' 같은 과도한 높임을 낮춘다
- **근거** 격식이 높아질수록 문장이 길어지고 거리감이 생긴다. 정중함과 존중은 다르다
- **적용** 전체 / **프로파일** yes(A1) / **민감도** 낮음
- **출처** S-01, S-04(극존칭 미사용)

### R-003 · 경어 제거의 부작용 처리
- **주장** 경어를 기계적으로 뺐을 때 어색해지면, **파악하려는 정보를 주어로 놓고 문장을 새로 쓴다**
- **근거** R-002를 규칙대로만 적용하면 비문이 나온다. 규칙의 부작용을 처리하는 상위 규칙이라
  값이 높다. 삭제가 아니라 재구성이 답이라는 패턴은 F1 수정 방법과도 같다
- **적용** 사용자 정보를 묻는 문장 / **프로파일** no / **민감도** 0
- **출처** S-01

### R-004 · 경어 허용 예외
- **주장** **사용자의 감정이 좋지 않을 상황(CS 문의, 반품·환불, 계정 제재)에서는 경어 의문형을 쓴다**
- **근거** 시스템이 확신할 수 없는 것을 사용자에게 물을 때, 낮은 경어는 단정처럼 읽힌다
- **적용** 질문형 문구 / **프로파일** no / **민감도** 중간
- **출처** S-01

# B. 태 · 극성

### R-005 · 능동형 기본
- **주장** 능동형을 기본으로 한다 (되다 → 하다, '~었' 빼기)
- **근거** 수동형은 행위자가 사라져 책임과 인과가 흐려진다
- **적용** 전체 / **프로파일** no / **민감도** 낮음
- **출처** S-01
- ⚠ **주의** 이 규칙은 **태**의 문제이지 시점 문제가 아니다. R-031(F1)을 대신하지 못한다

### R-006 · 수동형 허용 예외
- **주장** 세 경우엔 수동형이 낫다 — ① 서비스 종료·기간 만료 ② 사용자 행동의 결과인 인과를
  설명할 때 ③ 민감한 안내에서 사용자를 안심시킬 때
- **근거** ①은 주어(대상)를 강조하고 뉘앙스를 정확히 하며, ②는 인과를 명시하고,
  ③은 시스템이 주체임을 드러내 사용자 불안을 낮춘다
- **적용** 종료·만료·제재·정보 수집 안내 / **프로파일** no / **민감도** 높음
- **출처** S-01

### R-007 · 긍정형 전환
- **주장** 부정형을 긍정형으로 바꾼다 (없어요 → 있어요, 안 돼요 → ~하면 할 수 있어요)
- **근거** 사용자는 스캔하기 때문에 부정 표현을 보면 제품 전체를 못 쓴다고 넓게 해석한다
- **적용** 제한·불가 안내 / **프로파일** yes(A3) / **민감도** 높음
- **예외 조항(구 R-008 통합)** P-09(제한·불가)에서는 부정형으로 명확히 쓴다. 에러(P-07)에서는
  사실 보존이 우선한다(R-026·R-028) — 긍정형 전환이 지금 발생한 실패·제한을
  흐리면 적용하지 않고, 무엇이 잘못됐는지를 먼저 명시한 뒤에 가능한 조건을
  긍정형으로 안내한다 (2026-08-26 추가)
- **출처** S-01

### R-008 · 부정형 허용 예외 — **R-007로 통합 (2026-08-28, id는 인용 호환용으로 남김)**
- **주장** 정책상 사용 불가, 일부 기능 제한, 민감 정보 안내에서는 부정형을 쓴다
- **근거** 긍정형으로 감싸면 무엇을 못 하는지가 흐려져 사용자가 상황을 오인한다.
  명확성이 친절함보다 우선하는 지점
- **적용** 정책 제한 안내 / **프로파일** no / **민감도** 높음
- **출처** S-01

### R-009 · 강요 대신 권유
- **주장** '~해야 해요'가 아니라 '~할 수 있어요'로 쓴다
- **근거** 선택권이 사용자에게 있다는 감각을 유지시킨다. 공포를 조성해 유도하지 않는다
- **적용** 행동 유도 전반 / **프로파일** no / **민감도** 낮음
- **출처** S-02(Suggest over force), S-03

# C. 어휘 (F2)

### R-010 · 공급자 언어를 사용자 언어로
- **주장** 내부·업계 용어를 사용자가 아는 말로 바꾼다 (블라인드 → 숨김 처리, 토글 → 제외)
- **근거** 공급자 입장에서 정확한 말이 사용자에게는 아무 의미가 없다.
  UI 컴포넌트 이름을 그대로 쓰는 것이 대표적 실수
- **적용** 전체 / **프로파일** no / **민감도** 0
- **출처** S-06

### R-011 · 팀 내부 호칭 금지
- **주장** 기획 단계에서 팀이 부르던 이름을 제품 문구에 그대로 쓰지 않는다
- **근거** 팀에겐 익숙해진 단어가 사용자에겐 처음 보는 말이다.
  익숙함이 판단을 마비시키는 지점이라 의식적으로 점검해야 한다
- **적용** 기능명, 메뉴 레이블 / **프로파일** no / **민감도** 0
- **출처** S-07

### R-012 · 전문 용어 허용도 ⚠ 충돌
- **주장** 프로파일에 따라 갈린다. **최소**면 풀어쓰고, **적극**이면 그대로 쓰되 초출 1회 설명한다
- **근거** 토스는 일상에서 구두로 쓰지 않는 용어를 줄이라고 하고, 스켈터랩스는 통상적 전문
  용어를 적극 활용하되 과도하게 어려운 것만 지양하라고 한다. 대상 사용자가 그 용어를
  이미 쓰고 있는지가 갈림점이다
- **적용** 전체 / **프로파일** **yes(A2)** / **민감도** 낮음 / **충돌** —(프로파일로 해소)
- **출처** S-02(최소) ↔ S-04(적극), S-05(구름도 적극)

### R-013 · 표준 표기 vs 사용자 익숙함
- **주장** 규범상 맞는 표기와 사용자에게 익숙한 표기가 다르면 **익숙한 쪽**을 쓴다.
  **비슷한 도메인의 다른 서비스들에서도 보편적으로 쓰인다면 익숙하다고 판정한다**
- **근거** 표기 규범의 목적은 이해이지 준수 자체가 아니다.
  관용 표현은 예외로 둔다
- **적용** 외래어, 축약어 / **프로파일** no / **민감도** 0
- **출처** S-04

### R-014 · 명사 나열 풀기
- **주장** '{명사}+{명사}' 구조를 피하고 한자어를 동사로 풀어쓴다.
  풀기 어려우면 '{명사}가 {명사}해서' 형태로만 바꿔도 된다
- **근거** 명사 나열은 짧지만 읽는 사람이 관계를 추론해야 한다. 동사가 관계를 대신 말해준다
- **적용** 전체 / **프로파일** yes(A2) / **민감도** 0
- **출처** S-01

### R-015 · 소리 내어 읽기 테스트
- **주장** 눈으로 읽어 괜찮아도 **소리 내어 읽었을 때 어색하면** 고친다
- **근거** 검증 절차 자체가 규칙이다. 한자어, 문어체, 호흡이 긴 문장이 이 테스트에서 걸린다
- **적용** 전체 / **프로파일** no / **민감도** 0
- **출처** S-02(Easy to **speak**), S-04(소리내어 말하지 못하는 것 배제)

# D. 간결 · 밀도 (A4)

### R-016 · 문장 안 잡초 제거
- **주장** 넣든 빼든 의사 전달에 영향이 없는 단어를 제거한다
- **근거** 글자 수를 줄이는 게 목적이 아니라 **의미 없는 단어**를 없애는 것이 목적이다
- **조건 조항(구 R-020 통합)** 브랜드 특성에 '확신 톤'이 적힌 제품에서는 '바로·가장·빨리·새로운·간편한'
  같은 수식어와 느낌표를 쓴다. 그 제품에서 이 단어들은 **의사 전달에 영향이 없는 단어가 아니라
  전달하려는 내용 자체**라 이 규칙의 조건에 애초에 걸리지 않는다. 적혀 있지 않으면 잡초로 본다
- **적용** 전체 / **프로파일** **yes(밀도 + 브랜드 특성의 확신 톤)** / **민감도** 높음
- **출처** S-02(Weed cutting)

### R-017 · 화면 안 잡초 제거
- **주장** 한 화면에서 같은 말을 반복하지 않는다. 공간이 비어 보인다는 이유로 문장을 채우지 않는다
- **근거** R-016이 문장 안이라면 이건 화면 안이다. 층위를 나눠야 무엇을 자를지 판단이 선다
- **적용** 화면 단위 / **프로파일** yes(A4) / **민감도** 중간
- **출처** S-02(Remove empty sentences)

### R-018 · 화면 간 잡초 제거
- **주장** 사용자가 특정 흐름을 진행하고 있어서 이미 알고 있는 정보는 생략하거나 간략하게
  표현하고, 지금 알아야 하는 정보를 우선해서 남긴다
- **근거** 만드는 사람은 맥락을 많이 알아 다 설명하고 싶어진다. 그 압박이 사용자에겐 읽기 부담이다.
  때로는 생략이 더 친절하다
- **적용** 플로우 단위 / **프로파일** yes(A4) / **민감도** 중간
- **출처** S-02(Focus on key message)

### R-019 · 한 번에 한 논제
- **주장** 문장이 지리멸렬하지 않게 하나 혹은 두 가지 행동이나 주제만 담는다. 그렇다고 해서
  필요한 정보를 담은 문장을 제거하지 않고, 여러 문장으로 나누어 반드시 전달되게 한다.
  **이것은 글자수 판정(R-021)보다 우선이 될 수 있다**
- **근거** 후반부가 핵심이다. 간결함을 이유로 필수 정보를 버리면 R-025(에러 요건)와 충돌한다.
  줄이는 게 아니라 **쪼개는** 것이 답
- **적용** 전체 / **프로파일** no / **민감도** 낮음
- **출처** S-06, S-04(한 번에 한 가지)

### R-020 · 확신 수식어 허용 — **R-016으로 통합 (2026-08-28, id는 인용 호환용으로 남김)**
- **주장** 프로파일이 확신형이면 '바로, 가장, 빨리, 새로운, 간편한' 같은 수식어와 느낌표를 쓴다
- **근거** 토스가 잡초로 규정해 제거하는 단어를 강남언니는 브랜드 톤으로 적극 사용한다.
  **같은 단어가 제품에 따라 잡초도 되고 톤도 된다.** 정보량이 아니라 확신 전달이 목적일 때 살아난다
- **충돌 — R-016과 같은 단어를 두고 반대로 말한다** (양쪽 문장을 나란히 둔다)
  > 이 규칙: 프로파일이 확신형이면 '바로, 가장, 빨리, 새로운, 간편한' 같은 수식어와 느낌표를 쓴다
  > R-016: 넣든 빼든 의사 전달에 영향이 없는 단어를 제거한다

  **해소** 브랜드 특성에 확신 톤이 적혀 있으면 이 규칙이 이긴다. 그 제품에서 이 수식어들은
  "의사 전달에 영향이 없는 단어"가 아니라 전달하려는 내용 자체이므로 R-016의 조건에 걸리지 않는다.
  적혀 있지 않으면 R-016대로 잡초로 본다
- **적용** 기능 소개, 완료 안내 / **프로파일** **yes(A3 확신방향 + A4)** / **민감도** 높음 / **충돌** R-016

### R-021 · 컴포넌트 분량 제약
- **주장** 컴포넌트가 정해지면 그 분량 제약을 따른다. 짧게 사라지는 컴포넌트에 긴 설명을 넣지 않는다
- **근거** 컴포넌트 **선택**은 스킬 범위 밖이지만, 주어진 컴포넌트를 제약으로 받는 건 범위 안이다.
  **문장이 들어갈 장치나 컴포넌트, 위치와 역할에 따라 적정 글자수에 맞춰 작성한다.**
  다 담기지 않아도 문구는 내고 우려를 덧붙이되, **컴포넌트 이름을 대지 말고 필요한 성질을 말한다**
  ("다이얼로그가 낫습니다" ✗ / "사용자가 실행할 때까지 화면에 남아 있어야 합니다" ○)
- **적용** 전체 / **프로파일** no / **민감도** 높음(컴포넌트별)
- **출처** S-03(토스트에 과다한 내용), S-11(입력에 컴포넌트 포함)
- **분량 수치를 뺀 근거** (2026-08-20 결정 §1-13, 2026-08-26 실행본으로 흡수)
  이전 판 컴포넌트 표의 "제목+2문장", "1~4어절"은 전부 임의값이고 출처가 없었으며 해를 끼쳤다 —
  한 실행이 *"인라인 메시지 기본 제약인 1문장을 지켰습니다. 원인과 조치를 두 문장으로 나누면 더
  읽기 좋지만 제약 위반이라, 연결어미로 한 문장에 묶었습니다"*라고 판단했다. 더 나은 문구를
  알면서 수치 때문에 나쁜 쪽을 택한 것이다. **분량은 방향이지 정원이 아니다.** 제품 디자인
  시스템에 실제 글자 수 제약이 있으면 그것이 유일한 수치다

- **근거** 배민은 브랜드가 B급·유머로 유명하지만, **기능 소개 지점에만 위트가 있고
  과업 수행 지점에는 전혀 없다.** 같은 제품 안에서 최대 진폭으로 흔들리는 축이라
  기본값을 받는 방식이 맞지 않는다
- **적용** 기능 소개 허용 / 과업 수행·에러·확인 금지 / **프로파일** **yes(A5 허용 상황 목록)** / **민감도** **최고**
- **출처** S-08

# K. 스킬 동작 (메타 — 문구 규칙이 아님)

### R-043 · 수정 근거를 함께 제시
- **주장** 문구를 고칠 때 **어떤 규칙에 근거해 고쳤는지**를 함께 출력한다
- **근거** 라포랩스는 GPTs로 시도했을 때 가이드라인을 일부만 지키거나 없는 규칙을 지어내는
  문제를 겪었고, 준수 강제와 **근거 제시** 두 조건을 걸어 해결했다.
  **근거 제시가 환각 억제 장치로 작동한다** — F4 대응의 핵심
- **적용** 검수·생성 모두 / **프로파일** no / **민감도** 0
- **출처** S-09

### R-044 · 필수 입력 3종
- **주장** 첫 응답 전에 **타깃 사용자 / 사용자 목표 / 서비스 목표**를 확인한다
- **근거** 오늘의집과 라포랩스가 독립적으로 같은 세 항목에 도달했다.
  각각 하는 일이 다르다 — 타깃은 R-012(전문 용어)를, 사용자 목표는 R-028(추상화 수준)을,
  서비스 목표는 R-045(균형)를 판정한다
- **적용** 전체 / **프로파일** no / **민감도** 0
- **출처** S-10, S-09

### R-045 · 사용자 입장만으로 판단하지 않는다
- **주장** 서비스가 반드시 받아야 하는 절차가 있을 때, 사용자 편의만으로 문구를 결정하지 않는다
- **근거** 배민은 본인 확인처럼 귀찮지만 필수인 절차에서 균형을 잡아야 했다고 진술한다.
  다만 균형의 방법은 절차를 숨기는 게 아니라 **이유와 비용을 미리 알리는 것**이었다(R-025)
- **적용** 필수 절차, 동의, 인증 / **프로파일** no / **민감도** 0
- **출처** S-08, S-14(책 — 능동적으로 유도하는 텍스트)

### R-046 · 컴포넌트와 상황을 입력으로 받는다
- **주장** 문구 요청 시 컴포넌트와 상황을 함께 받는다. 없으면 묻는다
- **근거** 상황이 **무엇을 말할지**를, 컴포넌트가 **얼마나 길게 어떤 형식으로**를 정한다.
  구름의 검수 도구가 텍스트 외에 컴포넌트·맥락·상황을 받은 이유
- **적용** 전체 / **프로파일** no / **민감도** 0
